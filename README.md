# 县域农村自建房安全巡查整改补助平台

围绕**一栋房屋档案（同一安全事件）**打通「巡查 → 乡镇复核（整改方案）→ 风险告知 → 停用/人员转移清册化现场核对 → 施工计划与补助资格校验 → 施工材料/照片/进度 → 逐项验收 → 县级销号 → 销号后复查/整改期间现场核查」全链路，并把基层治理中的**协商成本**（户主、租户、经营者、老人家庭成员、村干部、施工队的态度与博弈）与 9 类异常事件沉淀在同一档案中。

**人员转移作为同一事件的核心环节**：档案中既有经营者、常住人员、租户、整改任务和补助申请，转移也按**一人一行的清册**管理——网格员在现场逐人核对「谁已离开、去了哪个安置点、从哪天开始安置、谁还在继续经营」并留存照片。登记 6 人只确认 5 人离开时，房屋保持「转移中（未清退）」，**不得标记已清退，开工、验收、销号、各类资金拨付全部停在对应环节；补助申请可保留、乡镇可核定**。整改期间经营者偷偷返回时，网格员的下一次现场核查**接着原事件处理（不新建记录）**：自动生成偷返阻断异常、撤销旧销号结论，劝返并全员复核后才能重新验收销号。全部人员转移且销号有效后，乡镇再处理**安置补助、经营损失补偿**，并单独决定**何时允许复营业**。

技术栈：Vue 3 + Vite + Element Plus + Pinia / NestJS 10 + TypeORM / PostgreSQL 15，Docker Compose 一键启动。

## 一、快速启动（Docker Compose 一键）

```bash
docker compose up -d --build
```

- 前端：http://localhost:8080
- 后端 API：经前端容器 nginx 反代在 http://localhost:8080/api （后端容器 3000 端口未直接发布到宿主机）
- PostgreSQL：容器内 `db:5432`，库名/账号/密码均为 `postgres`，数据库 `rural_house`

首次启动后端会**自动建表并写入演示数据**（7 栋覆盖各治理阶段的房屋、6 类角色账号、2 支施工队、3 个安置点）。重置数据：

```bash
docker compose down -v && docker compose up -d --build
```

## 二、本地开发启动（不用 Docker）

需本机 Node.js ≥ 20、PostgreSQL ≥ 13。

```bash
# 1. 建库
createdb -U postgres rural_house   # 或用 psql: CREATE DATABASE rural_house;

# 2. 后端（默认连接 localhost:5432, postgres/postgres）
cd backend
npm install
# 如数据库账号不同，用环境变量覆盖：
# export DB_HOST=localhost DB_PORT=5432 DB_USER=postgres DB_PASSWORD=postgres DB_NAME=rural_house
npm run start:dev          # http://localhost:3000，首次启动自动建表+演示数据

# 3. 前端（新终端）
cd frontend
npm install
npm run dev                # http://localhost:5173 （已配置 /api 代理到 3000）
```

后端环境变量：`DB_HOST DB_PORT DB_USER DB_PASSWORD DB_NAME JWT_SECRET PORT`。

## 四、核心业务规则与"互相制约"设计

### 1. 风险规则引擎（巡查登记即自动定级）

输入房龄、层数、经营、出租、加层、墙体裂缝/屋面渗漏/地基沉降（无/明显/严重）、居住人数、雨季因素：

- **紧急转移**：地基沉降严重；或严重墙裂+加层；或雨季叠加严重结构隐患；或严重结构隐患+人员聚集；
- **暂停使用**：存在加层；结构隐患叠加经营/出租/多层/多人居住；墙裂+沉降双明显；雨季叠加结构隐患；
- **限期整改**：任一明显结构缺陷、严重渗漏、高房龄多层等；
- **一般关注**：仅老旧、轻微渗漏、经营出租登记等，纳入日常巡查。

### 2. 环节互相制约（后端强制，非前端提示）

| 环节 | 闸口规则 |
|---|---|
| 风险告知 | 方案要求停用/转移的，告知**必须签收**，否则不能封停、不能转移、不能开工 |
| 人员转移清册 | 方案要求紧急转移的，必须先建立**一人一行清册**（户主/常住/租户/经营者/从业人员）；网格员现场逐人核对：已离开者必须登记**安置点、起始安置日期并上传照片**；仍在现场者可标注**继续经营** |
| 清退判定 | **只有清册全员现场确认离开才算清退**：登记 N 人仅 M<N 人离开 → 房屋保持「转移中（未清退）」，不得标记已清退；有人擅自返回 → 「问题反弹/续办」。未全员清退时**开工、验收、销号、补助拨付一律 400 拦截**，同时生成「人员未全部清退」督办异常留痕 |
| 停用/转移 | 未告知签收不得封停；转移人员**验收销号前不允许返回** |
| 整改期间现场核查 | 网格员复查发现偷返/偷营业，在**同一档案同一事件**内登记：生成「擅自返回/偷营业」**阻断异常**、清册人员置「擅自返回」、房屋转续办；若此前已销号则**旧销号结论自动撤销**、复营业准许收回；不会新建房屋记录 |
| 续办办结 | 偷返人员劝回安置点并**全员重新现场核对**后才允许办结阻断异常；未全员安置时办结被拒 |
| 阻断异常 | 农户拒改、租户不搬、偷换材料、补助争议、验收不通过、问题反弹、人员偷返等未办结时，**冻结开工/验收/销号**；办结必须填写处置结果 |
| 施工开工 | 须同时满足：已告知（且按要求签收）→ 已停用/已转移 → 户主签署整改同意书 → 施工队资质有效 → 预算明细完整；任一不满足直接 400 |
| 材料核验 | 施工日志填写的进场材料名称+规格与预算明细自动比对，不一致即判定**偷换材料**，自动生成阻断异常 |
| 补助申请 | 8 项资格校验（困难类型、困难证明、权属证明、户主同意、方案告知、高风险停用/转移、预算、施工队资质）全过才进入乡镇复核；金额 ≤ min(预算70%, 5万) |
| 补助审批 | 存在未办结**补助资格争议**时禁止批准 |
| 补助发放 | 即使已批准，**没有有效销号结论不得发放**（防"带病拨款"）；已发放不可重复发 |
| 安置补助 / 经营损失 | 全员转移后乡镇可持续受理：经营者申请经营损失、安置人员按「人天×标准」申请安置补助，**申请可保留、乡镇可核定**；拨付前再校验「全员清退 + 销号有效」，任一不满足一律停拨；核定金额不得超过申请额 |
| 复营业 | 经营房屋销号后仍默认停业；必须由乡镇/县级在「人员转移 · 复营业」页签**单独准许复营业**（可附条件）；销号被撤销时准许被收回 |
| 验收 | 必改项逐条给出结论，且施工状态必须"已完成"；方案要求全员转移的，清册未全员清退/有人偷返不得验收；任一条不合格→整体不通过→退回整改并开阻断异常 |
| 销号 | 仅"验收通过待销号"可销号；县级须勾选"逐项完成"与"安全恢复/非数字销号"双确认；**清册未全员清退不得销号**；销号后准许转移人员返回（经营场所仍须等复营业准许） |
| 复查反弹/续办 | 销号后复查 FAIL 或整改期间现场核查发现偷返 → 状态置为"问题反弹/续办"、回写新隐患、开阻断异常、**撤销旧销号**、清册重新进入现场核对；须重新复核→施工→验收→销号，全程同一档案，支持多轮治理 |

### 3. 协商成本建模

- **利益相关方台账**：户主/租户/经营者/老人家庭成员/村干部，记录态度（支持/观望/抵触）与对进度的影响；
- **协商记录**：议题、参与方、协商结果，进入档案时间线；
- **9 类异常事件**：农户拒绝整改、偷换材料、补助资格争议、雨季风险加重、租户不愿搬离、验收不通过、复查反弹、**整改期间擅自返回/偷营业**、**人员未全部清退**；区分是否阻断流程。

### 4. 县级看到的不是"数量销号"

驾驶舱直接暴露治理真实性指标：高风险房屋总数与**真正停用/处置率**、高风险未停用督办清单（点进即可处置）、销号率与**反弹数**、整改项逐条完成率（含不合格数）、**人员转移清册核对（登记/已安置/仍在现场/擅自返回/继续经营、全员清退栋数与偷返续办栋数）**、**安置补助与经营损失的申请/核定/拨付金额**、补助各环节数量与累计发放额、分乡镇对比。
