# 县域农村自建房安全巡查整改补助平台

围绕**一栋房屋档案**打通「巡查 → 乡镇复核（整改方案）→ 风险告知 → 停用/人员转移（逐人花名册现场核对）→ 施工计划与补助资格校验 → 施工材料/照片/进度 → 逐项验收 → 县级销号 → 销号后复查/偷返复查 → 安置补助·经营损失·复营业核准」全链路，并把基层治理中的**协商成本**（户主、租户、经营者、老人家庭成员、村干部、施工队的态度与博弈）与 8 类异常事件沉淀在同一档案中。

**人员转移与同一事件原则**：谁已离开、去了哪个安置点、从哪天开始安置、谁仍在继续经营，全部由网格员在**逐人花名册**上现场核对并留照片；登记 6 人只确认 5 人离开的，房屋不能标记为已清退，开工/验收/销号与补助拨付一律停在对应环节（补助申请可保留）。全部人员转移后继续办理安置补助、经营损失核定和复营业核准。经营者整改期间偷返的，下一次复查**接着原档案事件处理**（不新建记录），**旧销号结果自动作废**，重新清退→复核→施工→验收→二次销号。

技术栈：Vue 3 + Vite + Element Plus + Pinia / NestJS 10 + TypeORM / PostgreSQL 15，Docker Compose 一键启动。

## 一、快速启动（Docker Compose 一键）

```bash
docker compose up -d --build
```

- 前端：http://localhost:8080
- 后端 API：经前端容器 nginx 反代在 http://localhost:8080/api （后端容器 3000 端口未直接发布到宿主机）
- PostgreSQL：容器内 `db:5432`，库名/账号/密码均为 `postgres`，数据库 `rural_house`

首次启动后端会**自动建表并写入演示数据**（8 栋覆盖各治理阶段的房屋、6 类角色账号、2 支施工队）。重置数据：

```bash
docker compose down -v && docker compose up -d --build
```

## 二、本地开发启动（不用 Docker）

需本机 Node.js ≥ 20、PostgreSQL ≥ 13。

```bash
# 1. 建库
createdb -U postgres rural_house   # 或用 psql: CREATE DATABASE rural_house;

# 2. 后端（默认连接 localhost:5432, postgres/postgres）
cd backend
npm install
# 如数据库账号不同，用环境变量覆盖：
# export DB_HOST=localhost DB_PORT=5432 DB_USER=postgres DB_PASSWORD=postgres DB_NAME=rural_house
npm run start:dev          # http://localhost:3000，首次启动自动建表+演示数据

# 3. 前端（新终端）
cd frontend
npm install
npm run dev                # http://localhost:5173 （已配置 /api 代理到 3000）
```

后端环境变量：`DB_HOST DB_PORT DB_USER DB_PASSWORD DB_NAME JWT_SECRET PORT`。

## 四、核心业务规则与"互相制约"设计

### 1. 风险规则引擎（巡查登记即自动定级）

输入房龄、层数、经营、出租、加层、墙体裂缝/屋面渗漏/地基沉降（无/明显/严重）、居住人数、雨季因素：

- **紧急转移**：地基沉降严重；或严重墙裂+加层；或雨季叠加严重结构隐患；或严重结构隐患+人员聚集；
- **暂停使用**：存在加层；结构隐患叠加经营/出租/多层/多人居住；墙裂+沉降双明显；雨季叠加结构隐患；
- **限期整改**：任一明显结构缺陷、严重渗漏、高房龄多层等；
- **一般关注**：仅老旧、轻微渗漏、经营出租登记等，纳入日常巡查。

### 2. 环节互相制约（后端强制，非前端提示）

| 环节 | 闸口规则 |
|---|---|
| 风险告知 | 方案要求停用/转移的，告知**必须签收**，否则不能封停、不能转移、不能开工 |
| 停用/转移 | 未告知签收不得封停；要求紧急转移的必须建立**逐人花名册**并由网格员现场核对；批次登记人数不等于全员清退；转移人员**验收销号前不允许返回** |
| 清退口径 | **花名册逐人核对全员确认离开（含安置点、起始日、照片）才标记"已清退"**；登记 6 人只确认 5 人离开（或仍在经营）时，房屋保持"已停用"，开工/验收/销号全部拦截 |
| 阻断异常 | 农户拒改、租户不搬、偷换材料、补助争议、验收不通过、问题反弹、**偷返经营**等未办结时，**冻结开工/验收/销号**；办结必须填写处置结果 |
| 施工开工 | 须同时满足：已告知（且按要求签收）→ 已停用/**花名册全员清退** → 户主签署整改同意书 → 施工队资质有效 → 预算明细完整；任一不满足直接 400 |
| 材料核验 | 施工日志填写的进场材料名称+规格与预算明细自动比对，不一致即判定**偷换材料**，自动生成阻断异常 |
| 补助申请 | 8 项资格校验（困难类型、困难证明、权属证明、户主同意、方案告知、高风险停用/**全员清退**、预算、施工队资质）全过才进入乡镇复核；金额 ≤ min(预算70%, 5万)；未全过时申请保留为草稿、不进入复核队列 |
| 补助审批 | 存在未办结**补助资格争议**时禁止批准 |
| 补助/安置补助拨付 | 申请与乡镇核定可以保留，但即使已批准，**未有效销号不得发放/拨付**（防"带病拨款"）；销号作废后拨付同步被拒；已发放不可重复 |
| 验收 | 必改项逐条给出结论，且施工状态必须"已完成"；**花名册未全员清退不得验收**；任一条不合格→整体不通过→退回整改并开阻断异常 |
| 销号 | 仅"验收通过待销号"可销号；花名册全员清退与无未办结阻断异常为前置；县级须勾选"逐项完成"与"安全恢复/非数字销号"双确认；销号后准许转移人员安全返回 |
| 复查反弹 | 销号后复查 FAIL → **作废旧销号**、状态置"问题反弹"、回写新隐患、开阻断异常；须重新复核→施工→验收→销号，支持多轮治理 |
| 偷返复查 | 整改期间/销号后发现人员擅自返回或偷返经营，勾选人员（可留照片）即接着**原档案事件**处理：人员标"擅自返回"、旧销号作废、清退标记回退、开阻断异常；无需也不会新建房屋档案 |
| 经营损失 | 经营房可申报停业损失（流水/天数/金额+证明），乡镇核定金额，作为后续帮扶依据 |
| 复营业核准 | 仅**有效销号**后可申请复营业，乡镇核准并给出恢复营业起始日期；所依据销号作废的，核准一并失效，须重新申请 |

### 3. 协商成本建模

- **利益相关方台账**：户主/租户/经营者/老人家庭成员/村干部，记录态度（支持/观望/抵触）与对进度的影响；
- **协商记录**：议题、参与方、协商结果，进入档案时间线；
- **8 类异常事件**：农户拒绝整改、偷换材料、补助资格争议、雨季风险加重、租户不愿搬离、验收不通过、复查反弹、整改期间擅自返回/偷返经营；区分是否阻断流程。

### 4. 县级看到的不是"数量销号"

驾驶舱直接暴露治理真实性指标：高风险房屋总数与**真正停用/处置率**（要求紧急转移但花名册未全员清退的不计入已处置）、高风险未停用督办清单、**人员转移清退口径**（须转移/全员清退/未清退栋数、已离开·仍在·偷返人数、未全员清退督办明细）、销号率与**反弹数**、整改项逐条完成率（含不合格数）、整改补助与**安置补助**各环节数量与累计发放额、**经营损失核定与复营业核准**数量、分乡镇对比。
